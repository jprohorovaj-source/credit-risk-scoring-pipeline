## О проекте

**Credit Risk Scoring Pipeline** — end-to-end ML-проект по построению модели кредитного скоринга в условиях большого объёма данных и жёстких ограничений по оперативной памяти.

Основная задача проекта — разработать pipeline, способный обработать **26 млн строк**, подготовить данные для машинного обучения и построить модель, прогнозирующую вероятность дефолта клиента.

Главная инженерная особенность проекта — необходимость решить проблему потребления памяти до этапа обучения модели.

Вместо упрощения задачи за счёт уменьшения датасета была реализована **memory-efficient обработка полного массива данных** с автоматизацией контроля качества и оптимизацией типов.

Итоговый результат:

**пиковое потребление RAM снижено примерно в 6 раз — с 12 ГБ до 2 ГБ, а ROC-AUC модели после оптимизации достиг 0.7607.**

## Почему этот проект сложнее обычного ML-кейса

В классическом ML-проекте можно начать с загрузки готового датасета в память и сразу перейти к EDA и обучению модели.

Здесь такой подход приводит к проблемам:

```text
26 млн строк
       ↓
загрузка исходных типов
       ↓
высокое потребление RAM
       ↓
OOM / невозможность продолжить обработку
```

Поэтому первым объектом оптимизации становится не модель, а **сам pipeline обработки данных**.

Инженерная задача проекта:

```text
Большой датасет
       ↓
Контроль памяти
       ↓
Оптимизация типов
       ↓
Поколоночный downcasting
       ↓
Обработка частями
       ↓
Валидация результата
       ↓
Готовый ML-дataset
       ↓
Обучение модели
       ↓
Optuna
       ↓
ROC-AUC = 0.7607
```

Особенность задачи — значительный дисбаланс классов, поэтому при обучении необходимо учитывать различную стоимость ошибок и корректно выбирать метрики оценки.

## Основные инженерные задачи

### 1. Обработка 26 млн строк

Первой задачей стала организация обработки полного датасета без потери данных из-за ограничений оперативной памяти.

Основной принцип:

**не уменьшать задачу, а уменьшать стоимость её представления в памяти.**

Для этого pipeline анализирует типы данных и применяет оптимальное представление колонок.

---

### 2. Агрессивный downcasting

Для числовых признаков применяется понижение разрядности типов там, где это безопасно.

Например:

```text
int64  → int32 → int16 → int8
float64 → float32
```

Выбор типа выполняется с учётом диапазона значений, чтобы оптимизация памяти не приводила к потере данных.

Такой подход позволяет значительно сократить объём памяти, занимаемый DataFrame.

---

### 3. Поколоночная оптимизация

Оптимизация выполняется не только для всего DataFrame целиком, но и на уровне отдельных колонок.

Для каждого признака анализируются:

* текущий тип;
* диапазон значений;
* необходимость целочисленного или вещественного представления;
* возможность безопасного уменьшения разрядности.

Это позволяет использовать память значительно эффективнее, чем при хранении всех числовых признаков в стандартных `int64` / `float64`.

---

### 4. Chunk-based processing

Большие массивы обрабатываются частями.

Общая схема:

```text
Raw data
   ↓
Chunk 1 → optimize → validate → aggregate
   ↓
Chunk 2 → optimize → validate → aggregate
   ↓
Chunk 3 → optimize → validate → aggregate
   ↓
...
   ↓
Final dataset
```

Такой подход предотвращает необходимость одновременно хранить весь исходный массив в оперативной памяти.

---

### 5. Автоматизация контроля качества

В pipeline предусмотрена автоматическая валидация результатов обработки.

Контролируются ключевые характеристики данных до и после преобразований, чтобы оптимизация памяти не нарушала структуру датасета.

Таким образом, memory optimization становится частью воспроизводимого pipeline, а не ручной операцией перед обучением модели.

## Machine Learning

После подготовки данных задача переходит к построению модели бинарной классификации.

Основной алгоритм — **LightGBM**, градиентный бустинг по деревьям решений, хорошо подходящий для:

* табличных данных;
* большого количества наблюдений;
* нелинейных зависимостей;
* задач бинарной классификации;
* работы с признаками различной природы.

## Оптимизация гиперпараметров

Для автоматизации поиска параметров модели используется **Optuna**.

Вместо ручного перебора параметров pipeline формирует пространство поиска и автоматически исследует различные комбинации гиперпараметров.

Общая схема:

```text
Baseline model
       ↓
Определение пространства поиска
       ↓
Optuna Trial
       ↓
Обучение LightGBM
       ↓
Оценка ROC-AUC
       ↓
Следующий Trial
       ↓
Выбор лучшей конфигурации
```

Такой подход позволяет системно искать конфигурацию модели, обеспечивающую более высокое качество прогнозирования.

## Оценка качества

Основной метрикой проекта является **ROC-AUC**.

Для credit-risk задачи эта метрика позволяет оценить способность модели правильно ранжировать клиентов по уровню риска.

Чем выше ROC-AUC, тем лучше модель разделяет клиентов с различной вероятностью дефолта.
